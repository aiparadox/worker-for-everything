## 1. Purpose and non-responsibilities

**Purpose.** The Postgres adapter. It is the only code that writes SQL, and it implements `JobRepository` and the other repositories behind the ports. [DB: 1. Principles] [ARCH: 6. Code structure and the adapter rule] It owns every transaction boundary, lock and index choice for the eleven tables. [DB: 5. How the main operations touch the database]

**Does not do:**
- Business rules and state-transition rules. Those live in `domain/`. [ARCH: 6. Code structure and the adapter rule]
- Computing a retry delay. Callers pass a duration in, produced by [job-type-registry#next-retry-delay]. [ARCH: 10. Job types and handlers (how new work plugs in)]
- HTTP, credential checks, rate limits, RabbitMQ and storage calls. [ARCH: 6. Code structure and the adapter rule]
- Schema changes. Those are Alembic migrations run by [platform#migrate-job]. [DB: 12. Migrations and change process]
- Choosing retention values. They are configuration. [DB: 10. Retention and cleanup]

## 2. Interfaces provided

Conventions for every interface below:
- Every read or write on organisation-owned data takes `organisation_id` and filters on it. [DB: 1. Principles]
- Anything compared with "now" uses the database clock, never the application clock. [DB: 2. Conventions]
- Results are typed outcomes (for example `refused`, `lease-lost`), not HTTP codes. The sources define no error type names. [ASSUMPTION DA-01]
- Ids are UUIDv7, generated by the database default or by the application. [DB: 2. Conventions]

## 5. Internal workflow

### 5.1 `submit-job-tx`

1. Open a transaction. [DB: jobs; §5 Submit job]
2. Take the organisation's advisory lock with `pg_advisory_xact_lock`, whose key is a 64-bit value derived from the organisation id. A collision between two organisations only causes extra waiting. [DB: jobs; §6] [NOTEPAD: Phase 0 verification results]
3. If `idempotency_key` is given and a job exists for `(organisation_id, idempotency_key)`: return `existing` when `request_hash` matches, `idempotency-conflict` otherwise. [DB: jobs.idempotency_key; §5] [DB: jobs.request_hash]
4. Re-read the rows of `input_file_ids` and lock them with `FOR SHARE`. Each must be `available`, belong to the organisation and not be expired; otherwise return `file-unavailable`. [DB: job_files; §4.8] [ARCH: 5. Life of a job]
5. Count active jobs (`queued`, `retrying`, `running`) for the organisation up to `cap + 1`. If the count exceeds the cap, return `cap-exceeded`. [DB: jobs; §6]
6. Insert the `jobs` row with status `queued`, `run_at = now()`, `attempts = 0`, `sweep_count = 0`, `last_enqueued_at = now()`. [DB: jobs.run_at] [DB: jobs.sweep_count] [DB: jobs.last_enqueued_at] [ASSUMPTION DA-13]
7. Insert one `job_files` row per input file. [DB: job_files]
8. Insert one `outbox` row: `reason = submit`, `routing_key` = job type, `headers` with the trace id, `body` with the job id, `run_at = now()`. [DB: outbox.reason] [DB: outbox.routing_key] [DB: outbox.headers] [DB: outbox.body]
9. Commit, which releases the lock. [DB: jobs; §6]

The storage checks for the files happen before this interface is called. [ARCH: 5. Life of a job] [NOTEPAD: D36]

### 5.2 `claim-job`

1. One transaction. [DB: jobs; §5 Worker claim]
2. `UPDATE jobs` to `running` with `lease_owner`, a new random `lease_token`, `lease_expires_at = now() + lease`, `attempts = attempts + 1`, `sweep_count = 0`, and `started_at` set only if it was null, `WHERE id = :id AND status IN ('queued','retrying') AND run_at <= now()`. [DB: jobs; §5 Worker claim] [DB: jobs.started_at]
3. If zero rows changed, return `refused`. To name the reason the implementation has to read the current status and `run_at`. [DB: jobs; §5 Worker claim] [ASSUMPTION DA-10]
4. Otherwise insert a `job_attempts` row with the next `attempt_number`, `worker_id` and `started_at`, copying the job's `trace_id`. [DB: job_attempts.attempt_number] [DB: job_attempts.trace_id]
5. Commit and return `claimed`. The caller acks after this returns. [ARCH: 5. Life of a job]

### 5.3 `retry-job`

1. One transaction. [DB: jobs; §5 Retry]
2. `UPDATE jobs` to `retrying` with `run_at = now() + :delay`, `error`, and `last_enqueued_at = now()`, `WHERE id = :id AND status = 'running' AND lease_token = :token`. Zero rows changed means `lease-lost`. [DB: jobs.run_at; §5 Retry] [DB: jobs.lease_token]
3. Close the open `job_attempts` row with the outcome and error. [DB: job_attempts.outcome]
4. Insert an `outbox` row: `reason = retry`, the same `run_at`, `routing_key` = job type. [DB: outbox.reason] [DB: outbox.run_at]
5. Commit. [DB: jobs; §5 Retry]

### 5.4 Other worker writes

`heartbeat-job`, `finish-job-success` and `fail-job` are single guarded statements (plus closing the attempt for the last two), each with `WHERE id = :id AND status = 'running' AND lease_token = :token`. [DB: jobs; §5 Heartbeat] [DB: jobs; §5 Finish (success)] [DB: jobs; §5 Fail]

### 5.5 `rotate-refresh-token`

1. One transaction; the presented row is locked so two simultaneous refreshes are serialised. [DB: refresh_tokens; §5 Refresh token] [ASSUMPTION DA-14]
2. If `revoked_at` is set, return `revoked`. If the token's own `expires_at` has passed, return `expired`. If `now() >= family_expires_at`, return `family-expired`. [DB: refresh_tokens.family_expires_at] [DB: refresh_tokens.revoked_at] [DB: refresh_tokens.expires_at]
3. If `used_at` is null: set `used_at` and `replaced_by`, insert the new row with the same `family_id` and `family_expires_at`, and an `expires_at` that never goes past `family_expires_at`. Return `rotated`. [DB: refresh_tokens.replaced_by; §4.4]
4. If `used_at` is set and `now() - used_at` is within `reuse_window`: return `already-refreshed` and change nothing. [ARCH: 8. Authentication and authorisation]
5. Otherwise set `revoked_at` on every row of the family and return `reuse-detected`. [DB: refresh_tokens.revoked_at; §4.4]

### 5.6 `recover-expired-leases`

1. Find candidates with `status = 'running'` and `lease_expires_at < now()` using the partial index on running jobs. [DB: jobs; Indexes]
2. For each candidate, one transaction: lock the job with `SKIP LOCKED` and re-check that it is still running with an expired lease. [DB: jobs; §5 Recover]
3. If `attempts >= max_attempts`: set `failed` and close the open attempt as `lease_lost`. [DB: jobs; §5 Recover] [DB: job_attempts.outcome]
4. Otherwise: ask the caller's `delay_for(job)`, set `retrying` with `run_at = now() + delay`, close the attempt as `lease_lost`, insert an `outbox` row (`reason = recovery`) with the same `run_at`, and set `last_enqueued_at`. [DB: jobs; §5 Recover]

### 5.7 `sweep-waiting-jobs`

1. Candidates: `status IN ('queued','retrying')`, `run_at < now() - wait`, `last_enqueued_at < now() - wait`, and no unpublished `outbox` row for the job, where `wait = 5 minutes * 2^sweep_count`, capped at 1 hour. [DB: jobs; §5 Sweep]
2. For each, one transaction with `SKIP LOCKED`: insert an `outbox` row (`reason = sweep`, `run_at = now()`), then `sweep_count = sweep_count + 1` and `last_enqueued_at = now()`. [DB: jobs; §5 Sweep] [DB: outbox.reason]
3. The caller logs a warning and counts each sweep. [NOTEPAD: D27]

## 6. Failure modes

| Step | If it fails | State left behind | Source |
|---|---|---|---|
| `submit-job-tx` before commit | The transaction rolls back; nothing is written, the lock is released | None | [DB: jobs; §5 Submit job] |
| `submit-job-tx`, unique violation on the idempotency index | The violation is caught and the existing job is returned | None | [DB: jobs; §6] |
| `claim-job` zero rows | Refused; caller acks and logs | None | [ARCH: 5. Life of a job] |
| `claim-job` crash before commit | The message was not acked, so RabbitMQ redelivers it | None | [ARCH: 5. Life of a job] |
| `claim-job` crash after commit, before the handler ends | The lease expires and recovery takes over | `running` with a lease that will expire | [ARCH: 5. Life of a job] |
| `retry-job`, `fail-job`, `finish-job-success`, `heartbeat-job` zero rows | `lease-lost`; the worker stops. The attempt was already closed as `lease_lost` by recovery | The newer attempt is untouched | [ARCH: 11. Reliability and delivery] |
| `fetch-due-outbox` batch, connection lost mid-batch | The transaction rolls back and the row locks are released; rows that were published but not yet marked are published again later | Possible duplicate message | [DB: outbox; §4.11 rules] |
| `record-publish-failure` inside a transaction that later rolls back | The failure count is lost with it | `publish_attempts` under-counted | [ASSUMPTION DA-15] |
| `recover-expired-leases` crash between candidates | Each job is its own transaction, so earlier jobs are done and later jobs stay for the next run | None | [DB: jobs; §5 Recover] |
| `purge-finished-jobs` | Deleted in batches by `id` range; a failed batch leaves its rows for the next run | None | [DB: 10. Retention and cleanup; jobs] |
| Postgres unavailable | Every operation fails; no part can submit, claim or publish | All writers stop | [DB: 1. Principles] |

## 7. Concurrency and idempotency

- **Duplicate submit with the same key.** The advisory lock serialises same-organisation submits, so the second sees the first's job. If both still collide, the unique index raises and the existing job is returned. [DB: jobs; §6] [DB: jobs.idempotency_key]
- **Different organisations** do not block each other. [DB: jobs; §6]
- **Two workers, one job.** The claim's conditional update lets only one win; the other changes zero rows. [DB: jobs; §5 Worker claim]
- **Stale worker.** Every worker write after the claim is guarded by status and lease token. [DB: jobs.lease_token]
- **Several relays or maintenance copies.** `FOR UPDATE SKIP LOCKED` keeps them off the same rows. [DB: outbox; §4.11] [ARCH: Containers (Docker Compose)]
- **Lock order inside `submit-job-tx`:** advisory lock, then file rows, then inserts. The sources do not say what other transactions take locks in a different order. [DB: jobs; §6] [ASSUMPTION DA-16]
- **Two simultaneous refreshes of one token** are serialised on the row lock, so exactly one rotates and the other lands in the reuse window. [DB: refresh_tokens; §5 Refresh token] [ASSUMPTION DA-14]
- **Idempotent repeats:** `revoke-token-family`, `revoke-api-key-row` and `mark-files-available` can be repeated without harm. [ASSUMPTION DA-17]

## 8. Performance notes

| `fetch-due-outbox` | Partial index `(run_at, id) WHERE published_at IS NULL`, `SKIP LOCKED`, batch | The transaction stays open while the relay publishes the whole batch with confirms [DB: outbox; §4.11] |

| `list-jobs` | `(organisation_id, id DESC)` and `(organisation_id, status, id DESC)` | Keyset pagination keeps cost flat per page [DB: jobs; Indexes] |

## 9. Security

- **Who may call this part:** only application code through the adapter; running services connect as `qfe_app`, which can read and write data but cannot change the schema. [DB: 9. Performance and tuning plan]
- **Tenant isolation** is enforced in application code by filtering every query on `organisation_id`, backed by a contract test that one organisation can never read another's jobs or files through any repository method. [DB: 1. Principles] [NOTEPAD: D34]
- **Secrets:** only hashes are stored (`key_hash` and `secret_hash`), never plain text. [DB: 2. Conventions]
- **Row-level security** is not used in Phase 1. [DEFERRED: Postgres row-level security as a second isolation layer]
- `list-attempts` relies on the join to `jobs` for isolation because `job_attempts` carries no `organisation_id`. [DB: job_attempts.job_id] [ASSUMPTION DA-09]
