# storage-adapter

Part 12 of 14. Draft for review. Tags are explained in [overview.md](overview.md) section 0.

## 1. Purpose and non-responsibilities

**Purpose.** The `StorageAdapter` port and its first implementation on an S3-compatible service, SeaweedFS in Docker. It makes upload links, download links, existence checks and deletes, and lets handlers read and write file contents. [ARCH: 6. Code structure and the adapter rule] [NOTEPAD: D6] [NOTEPAD: D20] Jobs carry file references and not file bytes, and neither the queue nor the database carries file contents. [NOTEPAD: D6]

**Does not do:**
- Keep the record of a file. The `files` row belongs to [file-api#create-upload-link] and [data-access#create-file-row]. [DB: files]
- Decide who may read a file. Ownership is checked by [file-api#verify-input-files] and by organisation-scoped queries. [ARCH: 5. Life of a job] [DB: 1. Principles]
- Scan uploads for viruses or content. [ARCH: 16. Security notes] [DEFERRED: virus or content scanning of uploads]
- Do multipart upload. Phase 1 is a single upload up to a size cap. [NOTEPAD: D31] [DEFERRED: multipart upload for very large files]
- Decide retention. It is configuration, backed by a bucket lifecycle rule. [DB: 10. Retention and cleanup]

## 2. Interfaces provided

| Interface | Params | Returns | Behaviour | Source |
|---|---|---|---|---|
| `create-presigned-upload` | `storage_key` (R, server-generated), `content_type` (R), `max_size` (R, the size cap), `expires_in` (R, short) | an upload URL and any form fields the upload needs | Signs a link locally, with no call to storage. The sources say "presigned upload URL" in the decision and "presigned POST policy with a size range" in the verification result, which return different shapes | [NOTEPAD: D31] [NOTEPAD: Phase 0 verification results] [CONFLICT C-04] |
| `create-presigned-download` | `storage_key` (R), `expires_in` (R, short) | a download URL | Short-lived; generated when a result or file is read and never stored | [DB: files] [NOTEPAD: D31] |
| `head-object` | `storage_key` (R) | `exists` (true or false), `size_bytes`, and optionally `content_type` | A server-side check that the object is in storage and how big it is. The comparison with the declared size is made by the caller | [ARCH: 5. Life of a job] [DB: files.size_bytes] |
| `delete-object` | `storage_key` (R) | `ok` or `not-found` | Removes the object. Used for unused uploads | [DB: 10. Retention and cleanup; files] |
| `read-object` | `storage_key` (R) | a stream of bytes | Lets a handler read an input file | [ARCH: 10. Job types and handlers (how new work plugs in)] [ASSUMPTION SA-02] |
| `write-object` | `storage_key` (R), a stream of bytes, `content_type` | `ok` | Lets a handler store a result file | [ARCH: 10. Job types and handlers (how new work plugs in)] [ASSUMPTION SA-02] |
| `ensure-bucket` | none | `ok` | Creates the bucket and its lifecycle rule if absent | [DB: 10. Retention and cleanup; Object storage] [ASSUMPTION SA-04] |

Errors are typed outcomes such as `unavailable` and `not-found`; the sources define none. [ASSUMPTION SA-09]

The handler receives "the storage adapter" in its context, so `read-object` and `write-object` are part of what a handler can call. Who turns a `file_id` into a `storage_key` for the handler is not stated. [ARCH: 10. Job types and handlers (how new work plugs in)] [ASSUMPTION SA-03]

## 3. Interfaces consumed

| From | Interface | How it is used |
|---|---|---|
| SeaweedFS S3 gateway | S3 API over HTTP: presigned URLs (SigV4), HeadObject, PostObject, delete, multipart (unused in Phase 1), bucket lifecycle get and put | Everything above. Supported per the project wiki; the POST policy size range is enforced in the upstream source. Not yet tested end to end | [NOTEPAD: Phase 0 verification results] |
| `platform` | [platform#startup-config-validation] | Credentials, bucket name and the **public storage URL** used in presigned links arrive as required configuration | [ARCH: 15. Configuration] [NOTEPAD: D31] |

Two addresses are probably needed: the public one that is signed into links, and an internal one for server-side calls from inside Docker. The sources require only the public one. [NOTEPAD: Phase 0 verification results] [ASSUMPTION SA-01]

The S3 client library is `boto3` run in a thread pool (D47). `aioboto3` must not be used. [ARCH: 18. Open items] [NOTEPAD: Phase 0 verification results]

## 4. Data

**Tables:** none read or written by this part. [DB: 7. Data that is not in Postgres]

**Storage objects it reads and writes:** one object per `files` row, found by `files.storage_key`, which is unique, generated by the server and namespaced by organisation. [DB: files.storage_key] [ARCH: 16. Security notes]

**Who else touches them:** clients upload directly through the presigned link, not through this part. [NOTEPAD: D31] A bucket lifecycle rule also removes objects, as a backstop. [DB: 10. Retention and cleanup]

## 5. Internal workflow

### 5.1 `create-presigned-upload`

1. Build the policy or link for exactly one `storage_key`, with the `content_type`, a size range up to `max_size`, and a short expiry. [NOTEPAD: Phase 0 verification results] [NOTEPAD: D31]
2. Sign it with the SigV4 scheme against the public storage URL, using local signing only. [NOTEPAD: Phase 0 verification results]
3. Return the URL and fields. Pinning the key and the content type in the policy is recommended but not stated. [ASSUMPTION SA-06]

### 5.2 `head-object`

1. Send a HeadObject request to the internal address. [NOTEPAD: Phase 0 verification results] [ASSUMPTION SA-01]
2. Return whether it exists and its size. [ARCH: 5. Life of a job]
3. The caller compares the size with the declared size or the cap. [DB: files.size_bytes]

### 5.3 `delete-object`

1. Send a delete for the key. [DB: 10. Retention and cleanup; files]
2. A missing object counts as success for the caller's purpose. [ASSUMPTION SA-09]

### 5.4 `ensure-bucket`

1. At startup, create the bucket if absent and apply a lifecycle rule matching the retention. [DB: 10. Retention and cleanup; Object storage] [ASSUMPTION SA-04]

## 6. Failure modes

| Step | If it fails | State left behind | Source |
|---|---|---|---|
| `head-object`: storage unreachable or slow | The submit that needs it cannot be checked; it fails before any transaction | No job; files stay as they were | [ARCH: 5. Life of a job] |
| `head-object`: object missing | The file is reported unavailable and the submit is rejected | None | [ARCH: 5. Life of a job] |
| `create-presigned-upload` while storage is down | Succeeds, because signing is local; the failure shows up when the client uploads | A `pending` row with a link that cannot be used yet | [NOTEPAD: Phase 0 verification results] |
| Client upload fails or is abandoned | The `pending` row expires and is purged | `pending` row until `expires_at` | [DB: files.expires_at] [DB: 10. Retention and cleanup; files] |
| Upload larger than the size range | Rejected by storage with an entity-too-large answer | None | [NOTEPAD: Phase 0 verification results] |
| Object removed (lifecycle rule, manual) after the check but before a worker reads it | The handler fails that job with a permanent error | Failed job | [NOTEPAD: D36] |
| `delete-object` fails after the `files` row was deleted | The object stays; only the lifecycle rule would remove it | Orphan object | [DB: 10. Retention and cleanup; Object storage] [ASSUMPTION SA-08] |
| Presigned link signed for the wrong host | Storage rejects the signature | Unusable link | [NOTEPAD: Phase 0 verification results] |
| Whether the size check happens before or after the body is read | Not verified | Large uploads may be fully received before being refused | [NOTEPAD: Phase 0 verification results] |

## 7. Concurrency and idempotency

- `delete-object` and `head-object` can be repeated safely. [ASSUMPTION SA-09]
- Keys are generated by the server and unique, so two clients cannot overwrite each other's objects. [DB: files.storage_key]
- A presigned upload link stays valid until it expires. After a file has been checked and marked `available`, a client that still holds the link could upload again, so the bytes a worker reads might differ from what was checked. [NOTEPAD: D36] [ASSUMPTION SA-05]
- Handlers must be safe to run twice, so a repeated `write-object` for the same job must give the same outcome. [ARCH: 10. Job types and handlers (how new work plugs in)] [ASSUMPTION SA-07]

## 8. Performance notes

Load assumptions are in [overview.md](overview.md) section 8. [ASSUMPTION L-01]

- **Submit latency:** every file in a payload costs one HEAD request before the transaction, and the decision's own example is 200 ms per call. Whether the calls run one after another or in parallel is not stated, and neither is a timeout. [NOTEPAD: D36] [ASSUMPTION SA-07]
- **Presigning** is local and cheap. [NOTEPAD: Phase 0 verification results]
- **File bytes** pass through worker processes when handlers read or write, so worker memory and bandwidth bound large files; the size cap's default is not set. [DB: 8. Write load and size limits] [ASSUMPTION SA-10]
- **Gateway:** one S3 gateway in Docker serves all clients and workers; its capacity is not discussed. [ARCH: Containers (Docker Compose)]
- **Unbounded:** none stated, apart from the size cap that is still a tuning value. [DB: 8. Write load and size limits]

## 9. Security

- Callers are internal: `file-api`, `worker` and `maintenance`. [ARCH: 6. Code structure and the adapter rule]
- Storage keys are generated by the server and namespaced by organisation, never taken from a client. [ARCH: 16. Security notes] [DB: files.storage_key]
- Links are short-lived and download links are never stored. [NOTEPAD: D31] [DB: files]
- No virus or content scanning in Phase 1. [ARCH: 16. Security notes]
- A leaked or reused upload link is the main exposure (see 7). [ASSUMPTION SA-05]
- Credentials are required configuration. [ARCH: 15. Configuration]
