# FEAT-20261010-1203: configuration module with startup checks

Status: **approved by the user on 2026-10-10** (all questions in the last section answered yes; recommendations accepted as written). Working branch: `feat-20261010-1203-config`, from `master` after `FEAT-1208`. Depends on: `FEAT-20261010-1208`. This spec also closes `ISS-20261010-1159` (tuning defaults) once approved.

## 1. What this builds and why

One place that reads settings from environment variables, checks them when a process starts, and stops the process with a clear message if anything required is missing or invalid (CLAUDE.md Module 4, ARCHITECTURE.md section 15). Plus a development `.env.example`.

## 2. Verified facts

- The rules come from `ARCHITECTURE.md` section 15 and `platform.md` section 2.2: required settings fail at start, tuning knobs may have code defaults, any fallback is named and logged.
- `platform.md` records that "which process needs which required setting" was never written down (ASSUMPTION PLT-01). This spec writes it.
- `pydantic-settings` 2.15.0 is on the dependency list (`FEAT-1208`). I have not yet run it; the behaviours in section 3.3 are checked in the tests this task adds.

## 3. Proposal

### 3.1 Shape

- Package `qfe.config`. One settings class per kind of process, all built on a shared base: `ApiSettings`, `WorkerSettings`, `RelaySettings`, `MaintenanceSettings`, `MigrateSettings`. A process loads only its own class, so the relay never needs the JWT secret.
- All variables start with `QFE_` (for example `QFE_DATABASE_URL`).
- Secrets use pydantic's secret type, so printing the settings object never shows their value.

### 3.2 Required settings, per process

"Required" = no default; the process will not start without it.

| Setting | api | worker | relay | maintenance | migrate |
|---|---|---|---|---|---|
| Database URL (app role `qfe_app`) | yes | yes | yes | yes | no |
| Database URL (migrator role `qfe_migrator`) | no | no | no | no | yes |
| RabbitMQ URL | yes | yes | yes | no (`maintenance.md` never touches the broker; it only writes outbox rows) | no |
| Valkey URL | yes | no | no | no | no |
| Storage endpoint (internal), access key, secret key, bucket | yes | yes | no | yes (file cleanup) | no |
| **Public storage URL** used in presigned links | yes | no | no | no | no |
| JWT secret, issuer, audience | yes | no | no | no | no |
| `WORKER_JOB_TYPES` (`*` = all, D39) | no | yes | no | no | no |
| Allowed web origins for CORS | yes | no | no | no | no |
| Service name, telemetry mode `QFE_TELEMETRY=on\|off`, and the OTLP endpoint (required only when the mode is `on`; `off` is logged once at startup, see `FEAT-1205`) | yes | yes | yes | yes | no |

Validation beyond "present": URLs must parse and have the right scheme; the JWT secret must be at least 32 characters; the public storage URL must not be a Docker-internal host name (checked as "not equal to the internal endpoint host"); `WORKER_JOB_TYPES` must be `*` or a comma list of names (that each exists is checked later by the registry, `FEAT-1212`).

### 3.3 Failure behaviour

- On any problem the process prints **all** problems at once (variable name and the reason, never the value) and exits with code 2. It does not stop at the first one.
- No value is guessed. A missing required value is never replaced by a default.
- Tests prove: missing variable, wrong type, short secret, empty string, and that a secret's value is absent from the error text and from `repr`.

### 3.4 Fallbacks

There are no silent fallbacks. If a later spec needs one (for example "Valkey down, fail open"), it is a named setting or a named code path that logs when it triggers. None is added by this task.

### 3.6 `.env.example`

A development file with obviously fake values (for example `QFE_JWT_SECRET=dev-only-change-me-dev-only-change-me`). It lists every required variable and, commented out, the tuning ones with their defaults. The real `.env` is git-ignored. Compose (`FEAT-1202`) reads it.

## 4. Tests

Unit tests only (no Docker): each settings class with a full valid set; one missing variable at a time; invalid values; secrets not leaked; the exit code and the all-problems-at-once message (tested through a small `load_or_exit` function).

## 5. Check for the same problem elsewhere

Lateral: every process type has its own class, so I checked the storage and broker rows in 3.2 against `worker.md` and `maintenance.md`: `maintenance` deletes storage objects of purged uploads, so it needs storage settings (the design listed them only for api and worker), and it never touches RabbitMQ, so it does not need that URL. The Valkey, JWT and relay rows follow `ARCHITECTURE.md` sections 4 and 15 and were not re-checked against the part files line by line. Causal depth: besides "missing", "present but wrong" (a Docker-internal public URL) is the second way config fails, and it is covered.

## 6. Out of scope

Reading secrets from a secret manager (deferred with production deployment, D43). Per-organisation limit overrides (deferred).
