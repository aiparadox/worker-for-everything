# FEAT-20261010-1210: domain layer, the job state machine and the retry delay

Status: **approved by the user on 2026-10-10** (option A for the retry defaults; the two smaller points were accepted as proposed). Working branch: `feat-20261010-1210-domain`, from `master`. Depends on: nothing. Used by: `FEAT-1211` (data access), `FEAT-1212` (job type registry), `FEAT-1216` (worker), `FEAT-1217` (maintenance).

## 1. What this builds and why

The two pieces of business logic that several parts must agree on, written once in `qfe/domain/` with no database, no network and no clock:

1. **The job state machine** as one transition table: which status a job may move to, on which event. The worker, the recovery job and the database operations all ask this table instead of each deciding for themselves.
2. **The "retry or fail" decision and the retry delay**, which the worker (handler failed) and `maintenance` (lease expired) must compute the same way, otherwise a job that crashes its worker behaves differently from one that raises an error (`ARCHITECTURE.md` sections 10 and 11).

Domain code never imports from `qfe.adapters` (the rule test from `FEAT-1206` already checks this).

## 3. Proposal

### 3.1 Status and the transition table (`qfe/domain/job_state.py`)

- `JobStatus` (a string enum with the six values) plus two sets: `LIVE_STATUSES` (`queued`, `retrying`, `running`: the ones counted by the active-jobs cap) and `FINAL_STATUSES` (`succeeded`, `failed`, `cancelled`).
- `JobEvent`: `CLAIM`, `SUCCEED`, `RETRY`, `FAIL`. (`CANCEL` is added in Phase 2, `FEAT-1237`, with its own spec because it also touches `running`.)
- **One table**, `TRANSITIONS`, mapping `(status, event)` to the new status. It holds exactly: `(queued, CLAIM)` and `(retrying, CLAIM)` to `running`; `(running, SUCCEED)` to `succeeded`; `(running, RETRY)` to `retrying`; `(running, FAIL)` to `failed`.
- `next_status(status, event)` returns the new status or raises `InvalidTransition` naming both. There is no other place in the code that decides a status change.

### 3.2 Retry or fail (`qfe/domain/retry.py`)

- `RetryPolicy` (immutable): `max_attempts`, `delays_seconds` (a tuple), `jitter` (a fraction). Checked when it is built, so a bad policy stops at registration or startup and never at the first failure: `max_attempts >= 1`; **at least `max_attempts - 1` delays** (no silent "repeat the last one": an explicit schedule per retry, Module 4); every delay positive; `0 <= jitter < 1`.
- `decide_after_failure(attempts, max_attempts, *, permanent)` returns `JobEvent.FAIL` when the error is permanent or `attempts >= max_attempts`, else `JobEvent.RETRY`. Used for a handler error and for a lease that expired (a lost lease counts as an attempt, so a job that crashes every worker fails after `max_attempts`).
- `retry_delay(policy, failed_attempt, random_unit)` returns a `timedelta`: the base delay for that attempt (`delays_seconds[failed_attempt - 1]`) times `1 + jitter * (2 * random_unit - 1)`, rounded to milliseconds. `random_unit` is a number in `[0, 1)` **passed in by the caller** (the application layer passes `random.random()`; tests pass fixed values), so the domain stays free of hidden randomness. It raises if `failed_attempt` is outside `1..max_attempts - 1`.

### 3.3 Settings (depends on question 1)

If you choose option A below, `FEAT-1203`'s `QFE_MAX_ATTEMPTS`, `QFE_RETRY_BASE_DELAY_SECONDS` and `QFE_RETRY_MAX_DELAY_SECONDS` are replaced in this task by `QFE_DEFAULT_MAX_ATTEMPTS` (4), `QFE_DEFAULT_RETRY_DELAYS_SECONDS` (`10,120,600`) and `QFE_DEFAULT_RETRY_JITTER` (0.2): the **default** policy for a job type that does not define its own (`FEAT-1212`). The configuration module builds a `RetryPolicy` from them, so a bad value stops the process at startup. `.env.example`, `DATABASE.md` and the config tests are updated in the same commit.

## 4. Tests (unit, no Docker)

- **Every pair** of status and event is tried: the five legal ones give the table's result, all others raise `InvalidTransition`; no event leaves a final status; nothing leads back to `queued`.
- The enum values equal `JOB_STATUSES` in the database definition, and `LIVE_STATUSES` equals the statuses of the database's active-jobs index, so the domain and the schema cannot drift.
- `decide_after_failure` over a grid of attempts and `max_attempts`, permanent or not. A loop that applies it until the job fails shows that a job that always fails runs exactly `max_attempts` times and is retried `max_attempts - 1` times (the crash-loop guarantee).
- `retry_delay`: with `random_unit` 0, 0.5 and just under 1 the result is the base times 0.8, 1.0 and just under 1.2 (jitter 0.2); no jitter gives exactly the base; the base grows along the schedule; results are positive and never exceed `base * (1 + jitter)`; an attempt outside the range raises.
- `RetryPolicy` rejects: no attempts, too few delays, zero or negative delay, jitter below 0 or 1 and above.
- With option A: config defaults equal 4 / 10, 120, 600 / 0.2, the `.env.example` lines match the code defaults (the existing drift test), and a bad schedule stops startup with a clear message.

## 5. Check for the same problem elsewhere

Lateral: the same "who decides the next status" question exists in every writer of `jobs.status`. This task defines the table; `FEAT-1211` must use it in each SQL operation (claim, finish, retry, fail, recover) and has a test that each operation's `WHERE status IN (...)` equals the table's source statuses. Causal depth: a job can end up in the wrong state because the table is wrong, because a caller bypasses it, or because the retry decision is computed twice in different ways (worker versus recovery); the first is covered by exhaustive tests here, the second by the `FEAT-1211` test, the third by having one `decide_after_failure` for both.
