# FEAT-20261010-1202: Docker Compose stack

Status: **draft for approval**. Working branch: `feat-20261010-1202-compose`, from `master` after `FEAT-1203`. Depends on: `FEAT-20261010-1201`, `FEAT-20261010-1203`, `FEAT-20261010-1208` (the app image installs the locked dependencies).

## 1. What this builds and why

`docker compose up` starts everything the system needs, so a new machine needs only Docker. This task builds the infrastructure services, the app image, the frontend image, an optional observability profile and the test profile (D48). It follows D43: development mode, so no ingress, TLS or backups.

## 3. Proposal

### 3.1 Files

`compose.yaml` at the repository root; `backend/Dockerfile`; `frontend/Dockerfile`; small config files under `deploy/` (RabbitMQ settings, SeaweedFS identities template, OTel settings if needed); `.dockerignore` files.

### 3.2 Services in this task

| Service | Image | Notes |
|---|---|---|
| `postgres` | `postgres:18` | named volume; health check `pg_isready`; role and database creation by the init script from `FEAT-1204` |
| `rabbitmq` | `rabbitmq:4-management` | named volume; `consumer_timeout` written explicitly in `rabbitmq.conf` (default 30 minutes, platform.md 2.5); health check `rabbitmq-diagnostics ping`; management page for development |
| `valkey` | `valkey/valkey:8` | counters only; no persistence needed in development; health check `valkey-cli ping` |
| `storage` | `chrislusf/seaweedfs`, **pinned tag chosen at the start** | one container running master, volume, filer and the S3 gateway; started with the S3 config file and `-s3.externalUrl` set from the public storage URL setting. Credentials are written into the identities file from environment variables when the container starts, so no secret is committed |
| `frontend` | built from `frontend/Dockerfile` (`node:22-slim`) | Next.js standalone build |
| `otel-lgtm` | `grafana/otel-lgtm`, profile `observability` | see 3.4 |

**Added by later tasks, not here** (their entrypoints do not exist yet): `migrate` (`FEAT-1204`), `api` (`FEAT-1205`, which adds `/healthz`), `relay` (`FEAT-1215`), `worker` (`FEAT-1216`), `maintenance` (`FEAT-1217`). `backend/Dockerfile` is built and checked in this task; each of those tasks adds its service entry using the same image with a different command.

Bucket creation is not done by a separate container. The storage adapter's `ensure_bucket` (`FEAT-1214`) does it, repeatably.

### 3.3 App image

Multi-stage `backend/Dockerfile` on `python:3.12-slim`: copy the `uv` binary from uv's published image, `uv sync --frozen --no-dev`, copy `backend/src`, run as a non-root user. One image, many commands (api, worker, relay, maintenance, migrate), as in ARCHITECTURE.md section 4.

### 3.4 Observability profile

`docker compose --profile observability up` adds **one** container, `grafana/otel-lgtm`, instead of the five separate containers in ARCHITECTURE.md. The apps only see one setting, the OTLP endpoint, so a later move to separate collector, Tempo, Loki, Prometheus and Grafana containers changes no app code. Reason: five containers on a development laptop are heavy (risk noted in ARCHITECTURE.md section 19), and the image states it is for development. **This changes the container list in the architecture doc for development only**, so I ask you to confirm it (question 1).

### 3.5 Ports and exposure

Every published port binds to `127.0.0.1`, so nothing is reachable from your network. Planned host ports: frontend 3000, api 8000 (when added), Postgres 5432, RabbitMQ 5672 and 15672 (management), Valkey 6379, storage S3 8333, Grafana 3001 (mapped, since 3000 is the frontend). If a port is taken, it is a variable in `.env`.

### 3.6 Test profile (D48)

`docker compose --profile test up -d --wait` starts a separate copy of `postgres`, `rabbitmq`, `valkey` and `storage` (service names with a `-test` suffix) on different host ports (for example 15432, 15672 and so on), with data on `tmpfs` so every run starts empty and nothing touches development data. They are defined once through `extends` so the settings are not copied by hand. Tests read their endpoints from `.env.test`, which is created from a committed `.env.test.example` with fake values.

### 3.7 Start order

Infrastructure health checks gate everything: `depends_on` with `condition: service_healthy`. One-shot services use `service_completed_successfully`. `--wait` makes `up` return only when health checks pass.

## 4. Tests and checks

- `docker compose config` passes for each profile (default, observability, test).
- `docker compose up -d --wait` brings the four infrastructure services to healthy; `docker compose down -v` leaves nothing behind.
- Reach each service from the host: `psql` through the container, the RabbitMQ management API, `valkey-cli ping`, an S3 call to port 8333.
- `docker build` of the backend and frontend images succeeds; the backend image runs as a non-root user.
- Everything starts a second time from a clean state with no manual step (idempotent).

## 5. Check for the same problem elsewhere

Lateral: every infrastructure service gets a health check and a localhost-only port, not just the first one written. Causal depth: "does not start" has two causes, a service that is not ready (health checks) and one that is up but misconfigured (the public storage URL, checked end to end in `FEAT-1209`).

## 6. Out of scope

Ingress, TLS, backups, secret management, published ports on the network (D43, deferred item `WISH-20261010-1309`); PgBouncer; the app services listed in 3.2.
